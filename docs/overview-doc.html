ALS-Dimmer: overview, algorithms and porting guide

ALS-Dimmer is a background daemon. It reads an ambient light sensor (ALS) and sets the brightness of a remote automotive display. This document tells you how the daemon operates, how to configure it, and how to move it to a different head unit.

Repository: als-dimmer Language: C++14 Target: Linux (Android and QNX by port) Style: ASD-STE100 (approximate)
Contents

    1About this document

    1.1 Purpose

    This document gives head-unit engineers the data that they need to:

    • Install and use als-dimmer on a Linux head unit without code changes.
    • Change the JSON configuration for a different sensor, display or vehicle.
    • Add a new sensor plugin or a new output plugin.
    • Port the code to Android or to QNX.

    1.2 Readers

    The readers are software engineers who work on infotainment head units. You must know C++, Linux processes, and I2C. You do not have to know the history of this project.

    1.3 Writing rules

    This document follows the rules of ASD-STE100 Simplified Technical English as much as possible. Thus:

    • Sentences are short. Procedural sentences have a maximum of 20 words.
    • Procedures use numbered steps. Each step has one instruction.
    • A WARNING tells you about a risk to persons, for example a driver who cannot see the road. A CAUTION tells you about a risk to equipment or data. A NOTE gives more data.

    2System summary

    The daemon runs a control loop. The loop period is update_interval_ms (default 500 ms). In each cycle, the daemon does these tasks:

    1. It reads the ambient light value from the sensor plugin.
    2. It finds the applicable zone (for example night, tunnel or daylight).
    3. It calculates a target brightness (0 to 100 %) from the zone curve.
    4. It moves the display brightness one small step toward the target.
    5. It writes the new value to the output plugin.

    A user or an HMI application can stop the automatic control. The daemon supports three operating modes:

    ModeBehaviorPersistent after restart
    autoThe sensor value controls the brightness.Yes
    manual_temporaryThe user value controls the brightness. After a timeout (default 60 s), the daemon goes back to auto.No. The daemon starts in auto.
    manualThe user value controls the brightness until the user selects auto again.Yes

    4.2 Threads

    The daemon uses few threads. Only the main thread changes the state and the hardware. Thus, the core does not need locks.

    • Main thread. Runs the control loop. Reads the sensor. Writes the output. Executes all commands.
    • Accept threads (one for TCP, one for Unix). Accept connections. Each accept thread starts one client thread for each connection.
    • Client threads. Read text lines and put them in the command queue. They do not execute commands.
    • Thermal poll thread. Only when thermal compensation is on. Reads the temperature every poll_interval_sec.
    NOTE

    The main thread executes the commands at the start of each cycle. Thus, a command can wait for a maximum of one loop period (500 ms by default) before it has an effect.

    4.3 One control cycle

    4.4 Start sequence

    1. The daemon reads the configuration file. If a value is not valid, the daemon stops with an error message.
    2. The daemon makes the ZoneMapper and the BrightnessController.
    3. The daemon reads the state file. If the file is missing, it uses defaults (auto, 50 %).
    4. The daemon makes the sensor plugin and calls init(). If this fails, it installs a NullSensor and sets manual mode.
    5. The daemon makes the output plugin and calls init(). If this fails, the daemon stops.
    6. The daemon restores the white point (FPGA displays only), loads the optional nits LUT and starts optional thermal compensation.
    7. The daemon opens the TCP socket and the Unix socket.
    8. If the saved mode is manual, the daemon writes the saved manual brightness. If the saved mode is manual_temporary, the daemon changes it to auto.
    9. The daemon starts the control loop.
    NOTE

    A failed sensor does not stop the daemon. A failed output stops the daemon. The display must stay controllable, but the daemon has no function without an output.

    5Plugin architecture

    5.1 The two interfaces

    The core uses only two abstract C++ classes. They are in include/als-dimmer/interfaces.hpp.

    SensorInterface

    class SensorInterface {
public:
  virtual bool  init() = 0;
  virtual float readLux() = 0;   // < 0 = error
  virtual bool  isHealthy() const = 0;
  virtual std::string getType() const = 0;
};
    • init(): open and configure the device. Return false on failure.
    • readLux(): return the light value. Return a negative value on error.
    • isHealthy(): return false when the last reads failed. The watchdog uses this.

    OutputInterface

    class OutputInterface {
public:
  virtual bool init() = 0;
  virtual bool setBrightness(int pct) = 0;  // 0..100
  virtual int  getCurrentBrightness() = 0;  // 0..100
  virtual std::string getType() const = 0;
  virtual bool setWhitePoint(int, int, int); // optional
};
    • setBrightness(): change 0..100 % into the hardware range and write it.
    • getCurrentBrightness(): return the last value in percent. The ramp starts from this value.
    • setWhitePoint(): only FPGA dimmers use it. The default returns false.

    5.2 How the core selects a plugin

    The selection is static. Each plugin .cpp file contains the class and a free factory function, for example createFileSensor(). The functions createSensor() and createOutput() in src/main.cpp compare sensor.type or output.type from the JSON file and call the applicable factory. There is no run-time library load (dlopen). Thus, the port to other operating systems is easy.

    5.5 Procedure: add a new sensor plugin

    Use src/sensors/file_sensor.cpp as a template. It is the smallest plugin.

    1. Make a new file src/sensors/my_sensor.cpp.
    2. Write a class that inherits from SensorInterface. Implement all four functions.
    3. In readLux(), return a negative value when the read fails. Set the health flag to false.
    4. Add a factory function std::unique_ptr<SensorInterface> createMySensor(...) in the namespace als_dimmer.
    5. Add a forward declaration of the factory near the top of src/main.cpp.
    6. Add an else if (config.sensor.type == "my_sensor") branch to createSensor().
    7. Add the type to Config::validate() in src/config.cpp. Otherwise the daemon rejects the configuration with "Unknown sensor type".
    8. If the plugin needs new JSON keys, add them to SensorConfig in config.hpp and parse them in config.cpp.
    9. Add the file to CORE_SOURCES in CMakeLists.txt.
    10. Add a sample file configs/config_my_sensor_*.json.
    CAUTION

    Do not block for a long time in readLux(). The main thread calls it in each cycle. A slow read delays the commands and the brightness ramp. Keep the read time much shorter than update_interval_ms.

    CAUTION

    A frozen sensor value looks the same as a constant light level. If your hardware has a sequence counter or a "data valid" bit, check it. Set isHealthy() to false when the data is stale. Refer to ioc_opt5001_sensor.cpp for an example.

    5.6 Procedure: add a new output plugin

    1. Make a new file src/outputs/my_output.cpp. Use file_output.cpp or fpga_sysfs_output.cpp as a template.
    2. Write a class that inherits from OutputInterface.
    3. In setBrightness(), clamp the input to 0..100. Scale it to the hardware range.
    4. Keep the last written percent value. Return it from getCurrentBrightness().
    5. If the hardware has a minimum value above zero, map 0 % to that minimum. Refer to ioc_tcon_output.cpp.
    6. Add the factory, the branch in createOutput(), the validation rule and the CMake entry. These are the same as in steps 4 to 9 of 5.5.
    WARNING

    Do not let the output go fully black in a moving vehicle unless your display specification permits it. A black display can hide warnings from the driver. Set the lowest brightness_range value in the night zone, or a hardware floor in the plugin, to keep the display readable.

    NOTE

    The ramp uses getCurrentBrightness() as its start point. If this function reads the hardware and the hardware gives a different scale, the ramp can stop or oscillate. Return the cached percent value.

    6Algorithms

    The automatic control has two stages. Stage 1 (zone mapper) changes lux into a target brightness. Stage 2 (ramp controller) moves the display toward the target in small steps. The two stages are independent. You can tune each stage in the JSON file.

    6.1Three zones for driving conditions

    The human eye adapts to light differently in different conditions. One single curve from 0 to 100 000 lux does not give good results. Thus, the daemon divides the lux scale into zones. Each zone has its own brightness range and curve. The shipped configurations use three zones:

    ZoneLux rangeBrightnessCurveTypical driving condition
    night0 – 105 – 30 %logarithmicNight drive, dark rural road, unlit tunnel, underground garage.
    indoor10 – 50030 – 70 %linearLit tunnel in daytime, dusk, dawn, heavy overcast, parking deck.
    outdoor500 – 100 00070 – 100 %logarithmicDaylight, direct sun on the display.

    The zone names are free text. The code does not use the names for decisions. You can define one zone, three zones or more. The daemon requires a minimum of one zone.

    Zone selection rule

    • The daemon examines the zones in the order of the JSON array.
    • A zone matches when lux_min ≤ lux < lux_max.
    • If no zone matches (lux is above all zones), the daemon uses the last zone.
    • A negative lux value means "no data". In auto mode, the daemon does not change the brightness in that cycle.
    CAUTION

    Make the zones continuous. The lux_max of one zone must be equal to the lux_min of the next zone. Also make the brightness ranges continuous. If there is a gap, the brightness jumps at the zone edge. The configuration check does not find gaps or overlaps.

    6.2Curves in a zone

    The daemon first clamps the lux value to the zone range. Then it calculates a normalized value n between 0 and 1. The target brightness is:

    target = bright_min + int( n × (bright_max − bright_min) )        // clamped to 0..100

    Linear curve

    n = (lux − lux_min) / (lux_max − lux_min)

    Use it when the zone range is small, for example 10 to 500 lux.

    Logarithmic curve

    n = ln(1 + lux − lux_min) / ln(1 + lux_max − lux_min)

    Use it when the zone covers a large range. The eye senses light approximately on a log scale. The "+1" prevents ln(0).

    6.3Hysteresis at zone edges

    Without hysteresis, a lux value near a zone edge can change the zone in each cycle. To prevent this, set control.hysteresis_percent (0 to 50, 0 = off, 5 to 15 is typical).

    When hysteresis is on, the daemon keeps the current zone while:

    lux_min × (1 − h/100)  ≤  lux  <  lux_max × (1 + h/100)

    Example with h = 5 and the default zones:

    • The display is in night (0 to 10). It goes to indoor only when lux is 10.5 or more.
    • The display is in indoor (10 to 500). It goes back to night only when lux is less than 9.5.
    NOTE

    In the hysteresis band, lux is outside the range of the current zone. The curve clamps lux to the zone edge. Thus, the target stays at the edge value of the current zone. With continuous brightness ranges, this gives no visible jump.

    6.4Smooth ramp (three-tier, asymmetric steps)

    The daemon never jumps directly to the target. In each cycle, it moves the brightness by one step. The step size depends on two things:

    1. The size of the error. A large error gives a large step. A small error gives a small step. Thus, the display moves fast at first and slows down near the target. There is no overshoot.
    2. The direction. Brightness up uses *_up steps. Brightness down uses *_down steps. The down steps are smaller.
    error = target − current
if      |error| > error_thresholds.large : step = large_up   or large_down
else if |error| > error_thresholds.small : step = medium_up  or medium_down
else                                     : step = small_up   or small_down
if |error| ≤ step : next = target                      // last step, no overshoot
else              : next = current ± step

    The step sizes and thresholds come from the zone that contains the new lux value.

    Why the down steps are smaller

    The eye adapts fast from dark to bright (pupil closes in less than 1 second). The eye adapts slowly from bright to dark (pupil opens in seconds, full dark adaptation takes minutes). Thus:

    • Tunnel exit: the display must become bright fast. Otherwise the driver cannot read it in the sun.
    • Tunnel entry: the display must become dark slowly. A sudden dark display is hard to read for eyes that are still adapted to daylight. A display that stays too bright for too long causes glare. The slow ramp is a compromise.

    Worked example (default zones, 500 ms cycle)

    EventLuxZoneStart → targetStepsTime
    Tunnel entryoutdoor → 2night60 % → 16 %28approx. 14 s
    Tunnel exit2 → 20 000outdoor16 % → 95 %15approx. 7.5 s
    NOTE

    To make the ramp faster, decrease update_interval_ms or increase the step sizes. A shorter interval also increases the number of sensor and output bus transactions.

    6.5Operating modes

    Rules

    • In auto, a brightness command changes the mode to manual_temporary and starts the timer.
    • In manual_temporary, each new brightness command restarts the timer.
    • When the timer reaches auto_resume_timeout_sec (default 60), the mode goes back to auto. The ramp then moves smoothly from the user value to the sensor target.
    • In manual, a brightness command changes only the value. The mode stays manual.
    • When a client selects manual, the daemon keeps the current brightness. Thus, the display does not jump.
    • A client cannot select auto when the sensor is not available. The daemon replies with error SENSOR_UNAVAILABLE.
    NOTE

    For a 1 to 2 minute temporary override, set auto_resume_timeout_sec to a value from 60 to 120.

    State persistence

    The state file (control.state_file) contains the mode, the manual brightness and the last automatic brightness. The daemon writes the file after each mode or brightness command and at shutdown. It writes a temporary file, calls fsync(), and renames it over the old file. Thus, a power loss during the write does not destroy the saved mode.

    CAUTION

    The default path in many sample configurations is /tmp/als-dimmer-state.json. On most systems, /tmp is cleared at boot. Then the manual mode does not survive a restart. Use a persistent path, for example /var/lib/als-dimmer/state.json.

    6.6Sensor watchdog and fallback

    The daemon must keep the display controllable when the sensor fails. Thus:

    1. If the sensor init() fails at start, the daemon installs a NullSensor. It sets manual mode.
    2. During operation, the daemon records the last time that isHealthy() was true.
    3. If the sensor stays unhealthy for sensor_failure_timeout_sec (default 30 s), the daemon replaces it with a NullSensor. It sets manual mode.
    4. If the manual brightness is 0 or less, the daemon uses fallback_brightness (default 50 %).
    5. get_status reports "sensor_status": "unavailable".
    NOTE

    The daemon does not try to use the sensor again after a fallback. Restart the daemon to recover the sensor.

    The option control.minimal_i2c = true stops sensor reads in the manual modes. Use it when the I2C bus is busy. The watchdog does not count the skipped reads as failures.

    6.7Optional: absolute brightness (nits) and thermal compensation

    These features do not change the automatic control. They let an HMI read and set the brightness in nits.

    • Brightness-to-nits LUT (brightness_to_nits). A CSV file maps brightness percent to measured nits. The daemon uses linear interpolation in both directions. Out-of-range requests are clamped and flagged. Make the table with tools/als-dimmer-sweep.py and a colorimeter.
    • Thermal compensation (thermal_compensation). A warm backlight gives 4 to 8 % fewer nits. The daemon reads the backlight temperature (direct I2C or a shell command), finds a factor in a CSV table and multiplies the LUT result by this factor. If the temperature is not available, the factor is 1.0.

    Refer to README.md, section "Adding or Updating a Display Calibration", for the full procedure.

    7Control interface

    7.1 Transport

    • TCP: 127.0.0.1:9000 by default.
    • Unix socket: /tmp/als-dimmer.sock by default. The file mode, owner and group are configurable.
    • Each message is one JSON object on one line. The daemon sends one JSON reply for each request.
    WARNING

    The interface has no authentication. Any client that can connect can change the display brightness. Do not set listen_address to 0.0.0.0 on a vehicle network. Keep TCP on 127.0.0.1, or turn it off and use only the Unix socket with restricted permissions.

    7.2 Request and reply format

    {"version":"1.0","command":"set_brightness","params":{"brightness":75}}

{"version":"1.0","status":"success","message":"Brightness set successfully","data":{"brightness":75}}

    7.3 Commands

    CommandParametersEffect
    get_status–Returns mode, brightness, lux, zone, sensor status, nits (if calibrated) and thermal data.
    get_config–Returns mode, manual brightness, last auto brightness, output type, calibration range.
    set_modemode: "auto" | "manual"Changes the mode. "manual_temporary" is rejected.
    set_brightnessbrightness: 0..100Sets the manual value. In auto, starts manual_temporary.
    adjust_brightnessdelta: −100..100Adds the delta to the manual value. Same mode rule as set_brightness.
    get_absolute_brightness–Returns percent and nits. Nits is null without a LUT.
    set_absolute_brightnessnits: ≥ 0Sets the brightness from a nits value. Needs a LUT.
    get_calibration_info–Returns LUT range, label, row count and thermal state.

    Error codes: INVALID_PARAMS, SENSOR_UNAVAILABLE, CALIBRATION_NOT_LOADED, UNKNOWN_COMMAND, PARSE_ERROR, INVALID_FORMAT, INTERNAL_ERROR.

    NOTE

    When an HMI slider sends many set_brightness commands quickly, the daemon keeps only the latest queued one. It never drops adjust_brightness commands, because each delta counts.

    7.5 Change notifications

    Set notification.enabled and notification.on_change_script. The daemon starts the script with two arguments: the event name and the new value.

    my-script.sh mode_changed       manual_temporary
my-script.sh brightness_changed 42
my-script.sh zone_changed       night

    The daemon sends an event only when the value changes. It sends a maximum of one brightness_changed event each second. The script runs in the background. The daemon does not wait for it.

    9Procedure: tune the zones for a new display

    Most head units can use the daemon without code changes. Usually you change only the JSON file.

    1. Select the sensor and output plugins. Set sensor.type, output.type, bus and address.
    2. Start the daemon with --foreground --log-level debug --csvlog /tmp/als.csv.
    3. Record the sensor value in each condition: night, tunnel, overcast day and direct sun.
    4. Set the zone edges between these values. Make the zones continuous.
    5. For each zone, find the lowest and highest comfortable brightness. Set brightness_range.
    6. Make the brightness ranges continuous at the zone edges.
    7. Set hysteresis_percent to 5 to 10.
    8. Drive through a tunnel. Look at the ramp time. Change the step sizes if necessary.
    9. Keep the down steps approximately half of the up steps.
    10. Use tools/visualize_csv.py to examine the CSV log.
    CAUTION

    If the sensor is behind the display glass (for example ioc_opt5001), the screen light adds to the reading. A white screen can then move the loop into a brighter zone, which makes the screen brighter again. Set each zone upper edge above the value that a full-white screen gives at that zone's maximum brightness. Refer to configs/config_ioc_opt5001_tcon_ots17.json.

    NOTE

    The algorithm does not need real lux. If the sensor gives raw codes, set scale_factor to 1.0 and write the zone edges in codes.

    10.2 Test without hardware

    2. Write a lux value: echo 2 > /tmp/als_lux.txt.
    3. Read the brightness: cat /tmp/als_brightness.txt. The value decreases step by step.

    11Port to Android

    Android uses the Linux kernel. Thus, the I2C, sysfs and socket code works. The changes are in the build, the start and the security policy.

    11.1 Procedure

    1. Build the daemon with the Android NDK. CMake works with the NDK toolchain file. Alternatively, write an Android.bp file with cc_binary.
    2. Remove the ddcutil output from the build. Keep USE_DDCUTIL=OFF.
    3. Install the binary in /vendor/bin/. Install the configuration in /vendor/etc/als-dimmer/.
    4. Write an init .rc file. Use class hal or class main. Set user and group with access to the I2C device.
    5. Set the Unix socket path to a directory that the daemon can write, for example /data/vendor/als-dimmer/. Set the state file in the same directory.
    6. Write the SELinux policy. The daemon needs access to the I2C device nodes, its data directory and its socket.
    7. Turn off the TCP socket if no client uses it.
    8. Connect the HMI. A vendor service or a HAL can send JSON commands to the Unix socket.
    CAUTION

    Android has its own automatic brightness function. If Android and als-dimmer both control the same display, they fight. Turn off the Android adaptive brightness for this display. Or make Android send its slider value to als-dimmer with set_brightness.

    12.1 Procedure

    1. Build the core and the file plugins first. Use the QNX SDP CMake toolchain (qcc, C++14).
    2. Run the simulation test of 10.2 on the QNX target. This proves the core, the sockets and the threads.
    3. Write a small I2C helper with two functions: write bytes, and write-then-read bytes. Implement it with devctl().
    4. Change one sensor plugin and one output plugin to use the helper. Start with the plugins that your display uses.
    5. Exclude the Linux-only plugins from CORE_SOURCES on QNX. Remove their branches from the factories with #ifdef.
    6. Replace fork() + execl() in notifier.cpp with posix_spawn().
    7. Add an SLM entry. Restart the daemon if it stops.
    8. Do the zone tuning of section 9 on the vehicle.
    NOTE

    Do not change zone_mapper.cpp, brightness_controller.cpp or state_manager.cpp during the port. They contain no platform code. If you keep them the same, all platforms behave identically.

    13Known behaviors and limits

    These items come from a review of the code. Read them before you tune or port the daemon.

    #ItemEffectWhat to do
    1The short step keys large, medium, small are read but not used.The ramp uses only the six *_up/*_down keys. If a zone has only the short keys, the defaults apply (up 10/4/2, down 5/2/1). The parser gives no warning. All shipped configurations use the six direction keys.Always write the six direction keys. To convert old values, use up = old value and down = old value ÷ 2, rounded up.
    1aconfig_fpga_opti4001_ddcutil.json and config_fpga_opti4001_lux_ddcutil.json have no output.device.The daemon rejects these two configurations at start.Add "device": "/dev/i2c-1" (or your bus) to the output block before use.
    2sensor_error_timeout_sec is read but not used.Only sensor_failure_timeout_sec (default 30 s) controls the fallback.Set sensor_failure_timeout_sec.
    3adjust_brightness adds the delta to the stored manual value, not to the current display value.In auto at 80 % with a stored manual value of 50 %, a delta of +10 gives 60 %.From an HMI in auto, prefer set_brightness with an absolute value.
    4The "simple" mapping without zones cannot be reached.The configuration check requires a minimum of one zone.Define zones.
    5The sensor types veml7700 and custom_i2c, and the output types custom_i2c and can, pass the configuration check but have no plugin.Sensor: the daemon falls back to manual. Output: the daemon stops.Do not use these types.
    6Many sample configurations put the state file in /tmp.manual mode does not survive a reboot.Use a persistent path.
    7The periodic state save in the loop depends on the loop time.The save after each command and at shutdown is reliable. The periodic save can miss a cycle.No action. Commands save the state immediately.
    8No authentication on the control sockets.Any local process can change the brightness.Restrict the socket permissions. Keep TCP on localhost.
    9A sensor is not used again after the watchdog fallback.The display stays in manual until restart.Let the service manager restart the daemon if necessary.
